# Имя файла из области скриншота

## Задача

Сохранённый файл должен называться по заголовку на скриншоте: имя репозитория, ключ задачи, вкладка редактора, тема письма. Сейчас имя собирается так:

`{timestamp}_{category}{extension}`

`category` приходит из Jev (`github_repo`, `jira_issue`, …) вместе с `confidence` и `probabilities`. Это тип экрана и число уверенности. Заголовок документа классификатор не возвращает и просить его об этом не нужно.

Заголовок читает Tesseract, и только из полосы экрана, где он обычно лежит. Классификация типа остаётся отдельным шагом на полном тексте.

## Куда вставить шаг

Текущая цепочка в `apps/back/src/services/upload.pipeline.ts`:

`preprocess` → `ocr` → `classify` → `save` → `cleanup` → `postprocess`

Новая цепочка:

`preprocess` → `ocr` → `classify` → `name` → `save` → `cleanup` → `postprocess`

`name` стоит после `classify`, потому что прямоугольник зависит от категории. В `save` слаг берётся из заголовка. Если заголовок пустой или короче 2 символов, слаг остаётся категорией, как сейчас.

Файл:

`{timestamp}_{slug}{extension}`

Пример: `2026-09-30_17-10-00_org-repo.png`, `2026-09-30_17-10-00_proj-123-login.png`.

## Где менять код

Менять только бэкенд. Фронт имя не назначает.

1. `apps/back/src/utils/ocr.ts`  
   Сейчас `runOcr` вызывает `tesseract <file> stdout -l eng --psm 3` и возвращает сплошной текст. Добавить рядом `runOcrTsv`: тот же вызов, последний аргумент формата — `tsv`. Текст для Jev собирать из слов TSV, второй прогон всего кадра не делать. `node-tesseract-ocr` в коде не используется, новый код тоже вызывает `execFile`.

2. Новый файл `apps/back/src/utils/title-regions.ts`  
   Карта `ImageCategory` → прямоугольник в долях ширины и высоты. Размер кадра брать из строки TSV `level === 1` (её `width` и `height`).

3. Новый файл `apps/back/src/utils/filename-from-ocr.ts`  
   Слова внутри прямоугольника, затем очистка слага. Для категорий без полосы функция сразу возвращает пустую строку.

4. `apps/back/src/services/upload.pipeline.ts`  
   Поле контекста `documentTitle?: string`. Шаг `name` пишет его. `saveStep` подставляет слаг: заголовок, иначе `ctx.category`.

5. `apps/back/src/types/jev.types.ts` и `apps/back/src/services/upload.service.ts`  
   В успешный ответ добавить `documentTitle?: string`. Категория и вероятности остаются.

6. `apps/back/README.md`  
   Одна строка в схему пайплайна и поле `documentTitle` в пример ответа. Источник правил — эта страница.

Jev (`apps/back/src/services/jev.service.ts`) не менять. Список из девяти категорий не становится списком заголовков.

## Как читать область

Один проход Tesseract, вывод TSV. Колонки слова: `level`, `left`, `top`, `width`, `height`, `conf`, `text`. Слово — это `level === 5`.

В полосу попадает слово, у которого пересечение с прямоугольником больше половины площади слова и `conf` больше 40. Слова сортируются по `top`, затем по `left`, склеиваются в строки с зазором по вертикали около 60% высоты строки.

После категории область резать нужно. У GitHub, Jira и IDE заголовок стоит в одной и той же части окна, и для каждого типа это своя полоса.

Единица — пиксели изображения, не сантиметры. В файле скриншота нет линейки экрана: одни и те же 2 см на мониторе дают разное число пикселей при масштабе 100%, 150% и 200%. Поле DPI в PNG чаще всего стоит как 96 и не совпадает с реальным экраном. Поэтому «стандартные сантиметры» в коде не на что умножить.

Высота полосы в долях кадра тоже не фиксируется. Заголовок сидит в шапке фиксированной высоты, а кадр бывает 768, 1080 или 1440 пикселей. Одна и та же доля на низком окне обрежет заголовок, на высоком захватит тело страницы. Скриншотов в `apps/back/test/fixtures/` нет, замерить наши кадры сейчас нельзя.

Полоса считается в пикселях от верха кадра. Масштаб берётся из TSV: медиана высоты слов в верхних 400 пикселях. Если она больше 24, интерфейс снят в масштабе 2, и потолок умножается на 2.

Высота полосы = потолок × масштаб. Ширина — как в таблице. Слова ниже этой линии в имя не идут.

Потолки для масштаба 1, от левого верхнего угла:

- `github_repo`: высота 160 px, x 0–1. Глобальная шапка GitHub обычно около 64 px, имя `owner/repo` и крошки — в следующих ~50 px. 160 px закрывает обе строки и не доходит до списка файлов.
- `jira_issue`: высота 180 px, x 0–0.7. Верхняя навигация Jira Cloud занимает 56 px. Ключ и краткое имя лежат сразу под ней. Правые 30% ширины — кнопки, их отсекаем.
- `ide_code`: высота 80 px, x 0–1. Вкладка файла в VS Code по умолчанию 35 px. 80 px хватает на строку заголовка окна и одну строку вкладок.
- `config_editor`: высота 80 px, x 0–1. Та же вкладка, что у IDE.
- `email_draft`: высоты нет. Тема письма стоит в разных местах у разных клиентов. Имя берётся поиском `Subject` / `Тема` по всему тексту OCR.
- `messenger_chat`: высота 72 px, x 0.15–0.7. Название канала в верхней полосе рабочей области. Узкий коридор по ширине отсекает список чатов слева и панель справа.
- `web_dashboard`: высота 160 px, x 0–0.8. У разных панелей шапка разная, 160 px — рабочий потолок, не замер.
- `system_notification`: полосы нет.
- `unknown`: полосы нет.

Строку внутри полосы подтверждает шаблон категории (`github.com/org/repo`, ключ `PROJ-123`, имя файла на вкладке). Если шаблон в полосе не нашёлся, тот же поиск идёт по всему тексту. Совпадение шаблона и есть проверка, что полоса попала в заголовок.

Дальше строка полосы чистится по категории. Если после очистки пусто, смотреть весь OCR-текст тем же правилом.

- `github_repo`. Сначала `github.com/<org>/<repo>`, затем первая строка вида `org / repo` или `org/repo`. Слаг: `org-repo`. Хвост вроде `tree`, `blob`, ветка — отрезать.
- `jira_issue`. Сначала ключ `[A-Z][A-Z0-9]+-\d+`. Если на той же строке есть короткий текст после ключа, добавить его. Слаг: `proj-123-login-fails`.
- `ide_code` и `config_editor`. Последний сегмент пути на вкладке (`src/ocr.ts` → `ocr.ts`). Расширение в слаге оставить.
- `email_draft`. Текст после `Subject` / `Тема`, без префикса.
- `messenger_chat` и `web_dashboard`. Первая непустая строка полосы, не длиннее 60 символов.
- `system_notification` и `unknown`. Заголовок не строить.

Слаг: нижний регистр, пробелы и `_` в `-`, оставить `[a-z0-9._-]`, схлопнуть дефисы, срезать с краёв, длина до 80. Пустой результат, короче 2 символов, или только дефисы — шаг `name` оставляет слаг категории.

В ответ API заголовок класть до санитизации, в имя файла — уже слаг. Сырой OCR на клиента не отдавать.

## Порядок на ближайшие два часа

1. `runOcrTsv` и сборка текста из TSV. Старый полный текст для `getCategory` сохранить по смыслу: те же слова, строки через перевод строки.
2. Карта прямоугольников и сбор строки полосы.
3. Правила слага по девяти категориям и запасной путь «весь текст», если полоса пустая.
4. Шаг `name` и смена слага в `saveStep`. В лог `onComplete` добавить заголовок.
5. Поле `documentTitle` в типе ответа и в `UploadService`.
6. Ручная проверка `POST /api/upload` на трёх видах: GitHub, Jira, IDE или конфиг. В фикстурах `apps/back/test/fixtures/` сейчас только `invalid.txt`, скриншоты png в репозитории отсутствуют. Для проверки нужны новые кадры. Ожидание: в пути есть слаг заголовка, `category` по-прежнему тип экрана. На уведомлении и на `unknown` путь остаётся `{timestamp}_{category}`.

Отдельную библиотеку обрезки (sharp, ImageMagick) в этот заход не ставить. Если слова в шапке систематически пустые, следующий шаг — вырезать прямоугольник и второй вызов Tesseract с `--psm 7` только для этой полосы.
